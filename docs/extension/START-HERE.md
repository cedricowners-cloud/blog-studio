## 지금 상태

- 2026-11-16: 개발을 시작했다. 작업 브랜치는 `feat/chrome-extension`이다. 아직 커밋하지 않았다.

- **E2, E3**: 글 채우기를 만들었고, **실제 네이버 화면에서 채워지는 것을 사용자가 확인했다.** 채운 글을 다시 읽은 문서도 넣은 것과 같았다. 인용구 6종과 구분선 8종을 모두 쓸 수 있다.
- **색 강조** (확장 0.2.0): `[pos]` 긍정, `[neg]` 부정, `[mark]` 형광펜. 색은 패널의 "색 설정"에서 정한다. 실제 네이버 화면에서 색으로 보이는 것까지 사용자가 확인했다.
- **글쓰기와 SEO 8단계** (확장 0.3.0): 확장 안에서 내 AI 키로 글을 만든다. 글쓰기 방식 6개와 SEO 8단계를 웹과 같은 프롬프트로 돌린다. 만든 글은 [채우기로 보내기]로 채우기 탭에 넘긴다.
  - 웹 폴더는 고치지 않았다. 웹의 글쓰기 코드를 확장 폴더에 옮겨 적었고, 웹과 같은 결과가 나오는지 시험이 확인한다 (`DESIGN-detail.md` 5.2).
  - 프롬프트는 확장 패키지에 넣지 않았다. `npm run prompts`로 만든 묶음 파일을 설정 탭에서 한 번 불러온다 (`DESIGN-detail.md` 5.3).
  - AI 키는 설정 탭에서 넣는다. [확인]을 누르면 쓸 수 있는 모델 목록을 받아 온다.
  - 화면은 탭 다섯 개다: 글쓰기, SEO 8단계, 채우기, 내 말투, 설정.
- **한 번에 끝까지 돌리기와 내 말투** (확장 0.4.0, 2026-11-17):
  - SEO 8단계를 시작할 때 "한 번에 끝까지"를 고르면, AI가 중간에 묻는 것(목적, 말투, 유도할 행동)을 미리 받고 끝까지 돌린다. 되묻는 단계에는 확장이 대신 답한다 (`DESIGN-detail.md` 5.12).
  - [내 말투] 탭에서 내 블로그의 공개 글을 모으고, AI가 말투를 정리한 카드를 만든다. 한 번에 돌릴 때 그 말투로 쓴다. 새 글이 생기면 찾아 넣고 말투를 새로 정리한다 (`DESIGN-detail.md` 7.6).
  - 한 단계씩 할 때는 초안 단계에서 [내 말투 넣기]로, 복사 방식에서는 [내 말투 복사]로 같은 말투를 쓴다.
  - 네이버는 확장 화면에서 직접 부르면 막는다 (403). 그래서 열려 있는 블로그 탭 안에서 읽는다.
  - 확장에만 있는 프롬프트(대신 보내는 답, 말투 정리)는 `extension/scripts/extension-prompts.ts`에 있다. 고치면 `npm run prompts`로 묶음을 다시 만든다.
  - 묶음의 형식 번호가 2로 올랐다. 0.3.0 때 불러온 묶음은 쓸 수 없고, 새로 만든 묶음을 다시 불러와야 한다.

  - DB에 표 두 개를 더했다: `prompt_packs`(묶음), `prompt_access`(받아도 되는 사람). 운영 DB에 적용했고, 지금 가입된 계정 하나를 목록에 넣었다. SQL은 `supabase/migrations/017_prompt_packs.sql`에 있다.
  - 프롬프트를 고친 뒤에는 `extension` 폴더에서 `npm run prompts:push`로 서버에 올린다.
  - 서버 주소와 공개용 키는 `extension/.env`에 있다 (git에 올라가지 않는다). 새 컴퓨터에서는 `.env.example`을 복사해 값을 채운 뒤 빌드한다.
  - 가입이 누구에게나 열려 있는 것을 확인했다. 프롬프트는 허락 목록으로 막았지만, 다른 표의 권한 규칙은 배포 전에 한 번 더 봐야 한다.
  - 0.5.2는 사용자가 실제로 확인했다 (2026-11-18): 메일의 링크로 로그인됐고, 비밀번호도 정했다.
- **사진 넣기** (확장 0.6.0, 2026-11-18):
  - 채우기 탭에서 본문의 이미지 자리(`[IMG: 설명]`)마다 내 컴퓨터의 사진을 골라 두면, 글을 채운 뒤 그 자리에 넣는다. [사진만 넣기]로 사진 단계만 다시 할 수 있다.
  - 방법: 사진을 에디터에 붙여넣어 네이버에 올린 뒤, 붙여넣기 전의 문서에 사진 부품만 끼워서 다시 넣는다 (`EDITOR-NOTES.md`의 사진 넣기, `DESIGN-detail.md` 4.3).
  - **실제 네이버 화면에서는 아직 확인하지 못했다.** 붙여넣기를 받는 곳(`input_buffer`)과 올라온 사진의 모양은 다른 확장의 동작에서 알아낸 것이고, 가짜 글쓰기 화면으로만 시험했다. 처음 써 볼 때 "사진 넣기 기록"을 받아 확인한다.
  - 사진을 구하는 다른 방법 중 블로그용 카드는 0.7.0에 만들었다 (아래). AI로 만들기와 무료 사진 찾기는 아직 없다.
- **블로그용 카드** (확장 0.7.0, 2026-11-18):
  - 채우기 탭의 "블로그용 카드 만들기"에서 글 맨 위의 표지 카드와 소제목마다 요약 카드 한 장씩을 만든다. 카드의 글을 읽고 고친 뒤 [카드를 글에 넣기]를 누르면, 본문에 카드 자리(`[IMG: 카드N - …]`)가 생기고 카드 그림이 그 자리의 사진이 된다. 올리는 것은 사진 넣기와 같은 길이다.
  - 카드의 내용은 웹의 카드 기능(`web/lib/cards-parser.ts`)과 같은 코드로 만든다 (`extension/lib/cards/parser.ts`, 같은지는 `tests/parity.test.ts`가 본다). 그림은 사이드 패널에서 직접 그린다 (`render.ts`). 크기는 정사각형 1080×1080과 가로형 1200×900 중에서 고른다. 색은 채우기 탭 색 설정의 긍정 강조 색이다.
  - AI로 문구 다듬기는 고를 수 있고 기본은 꺼짐이다. 프롬프트는 웹의 것을 묶음에 담아 받는다 (`cards.rewrite`, 없어도 되는 글). **서버의 묶음을 새로 올려야** 확장이 받을 수 있다 (`npm run prompts:push`). 0.7.0을 만든 날에는 서버에 올리지 않았고, 0.9.0 때 사진 리뷰 프롬프트와 함께 올렸다 (2026-11-18).
  - 카드에 본문에 없는 숫자가 있으면 카드 아래에 알려 준다 (숫자를 통째로 견준다).
  - 0.9.0 (2026-11-18): 카드의 글씨체로 **Pretendard를 확장에 넣었다** (사용자 요청. `extension/public/fonts/`, 가변 글꼴 파일 하나 2MB, OFL 1.1). `lib/cards/font.ts`가 카드를 그리기 전에 불러온다. 확장 크기가 0.2MB에서 2.3MB가 됐다.
  - 0.8.0 (2026-11-18): 사용자가 카드가 투박하다고 해서 **카드 모양을 여덟 가지**로 늘리고 고를 수 있게 했다 (잡지, 색 띠, 부드러운 상자, 진한 바탕, 옆 번호, 메모지, 가운데 정렬, 기본). "블로그용 카드 만들기" 맨 위의 작은 그림을 눌러 고른다. 처음 값은 잡지다. 새 모양은 글을 카드 가운데에 모으고, 글자를 키우고, 본문에 있는 숫자를 색이나 형광펜으로 돋보이게 한다. "기본"은 웹과 같은 예전 모양 그대로다. 코드는 `lib/cards/designs.ts`(모양)와 `draw.ts`(도구)로 나눴다. 미리보기에서 여덟 가지를 정사각형·가로형, 짧은 글·긴 글로 확인했다. 서체는 0.9.0에 Pretendard를 넣었다.
  - 0.7.1 (2026-11-18): 사용자가 실제로 써 보고 잘 된다고 했다. 의견대로 [카드를 글에 넣기] 버튼을 카드들 아래로 옮겼다. 카드를 넣은 뒤 다시 만들면 카드 자리 글자가 카드 문구에 섞이던 것도 고쳤다.
  - 미리보기 화면에서 확인했다 (카드 그리기, AI로 다듬기는 가짜 AI로, 다시 넣어도 자리가 겹치지 않음). **실제 네이버 화면에 올라가는 것은 사진 넣기와 함께 아직 확인하지 못했다.**
  - 0.5.2 (2026-11-18): 0.5.1로도 로그인하지 못했다. 사용자는 메일의 링크를 그냥 눌렀고 (서버 기록으로 확인), 링크는 웹으로만 이어졌다. 그래서 **링크를 누르면 확장에 로그인되게** 고쳤다. 배경 코드가 도착한 탭의 주소에서 로그인 정보를 받아 간다 (`DESIGN-detail.md` 8장). `.env`에 `WXT_WEB_URL`(웹 주소)이 있어야 한다.
  - 0.5.1 (2026-11-18): 사용자가 비밀번호를 몰라 로그인하지 못했다 (메일 링크로만 로그인해 왔고, 웹에는 비밀번호 정하는 화면이 없다). 그래서 확장에 **메일로 로그인**(6자리 코드, 또는 메일의 링크 주소 붙여넣기)과 **비밀번호 정하기**를 넣었다. 메일에 6자리 코드가 오게 하려면 Supabase의 Magic Link 메일 양식에 `{{ .Token }}`을 넣어야 한다 (`DESIGN-detail.md` 8장).
- **자료 찾기** (확장 0.10.0, 2026-11-18):
  - 사용자 요청: 네이버 API 키가 있으니, 쓰려는 글의 자료(관련 뉴스, 블로그 글)와 키워드를 확장에서 찾고 싶다.
  - 새 탭 "자료" (`research-section.ts`). 찾을 말을 적으면 세 가지를 한꺼번에 찾는다: 키워드의 한 달 검색 수와 연관 키워드(검색광고 API의 키워드 도구), 그 말로 윗자리에 나오는 블로그 글 10개, 관련 뉴스 10건(검색 API). 코드는 `lib/naver/api.ts`이고, 웹의 `web/lib/naver.ts`와 같은 주소와 서명 방식을 쓴다.
  - 메인·서브 키워드와 참고할 글(블로그 5개, 뉴스 5건까지)을 고르고 [글쓰기에 넣기]를 누르면, 글쓰기 탭의 키워드 칸이 채워지고 고른 글이 프롬프트에 붙는다. 블로그 글은 웹의 "상위 글 조사"와 같은 자리(`research_context`)에, 뉴스는 그 뒤에 붙는다 (`news_context`, 확장에만 있다). 제목과 요약만 보내고 본문은 가져오지 않는다.
  - 네이버 키 (0.11.0에서 바뀜): **가족이 함께 쓰는 키를 서버에 올려 두고, 로그인하면 받아 온다.** 사용자가 "암호화해서 같이 올려 달라, 가족 공용으로 쓰겠다"고 했다. 확장 파일이나 GitHub에 넣으면 암호화해도 푸는 열쇠가 같이 들어가서, 대신 서버에 두고 로그인한 가족만 받게 했다. 표는 `shared_keys` (`supabase/migrations/018_shared_keys.sql`), 읽을 수 있는 사람은 프롬프트와 같은 목록(`prompt_access`)이다. 올리는 명령은 `npm run keys:push` (`web/.env.local`의 `NAVER_*` 다섯 줄).
    - 2026-11-18에 사용자 확인을 받고 표를 만들고 키 5개를 올렸다. 실제 DB에서 확인했다: 목록에 있는 계정은 읽고, 다른 계정·로그인하지 않은 요청은 읽지 못하고, 누구도 쓰거나 지우지 못한다.
    - 확장은 로그인할 때와 [프롬프트 새로 받기]를 누를 때 공용 키를 받는다 (`syncSharedKeys`). 설정에서 직접 넣은 키가 있으면 그것을 쓴다. 로그아웃하면 서버에서 받은 키는 지운다.
    - 가족을 더하려면 `prompt_access`에 그 계정을 넣는다 (017 파일의 머리에 방법이 있다). 그러면 프롬프트와 네이버 키를 함께 받는다.
    - 알아 둘 점: 검색광고 API 키는 키워드 조회뿐 아니라 그 광고 계정을 다루는 데도 쓸 수 있다. 사용자에게 알렸고, 사용자가 5개를 모두 올리기로 했다.
    - 설정의 "네이버 API 키" 칸에 직접 넣을 수도 있다. `.env` 파일의 줄을 통째로 붙여넣으면 키 5개를 골라낸다.
  - 0.12.0 (2026-11-18): 사용자 의견대로 결과를 다 볼 수 있게 했다. 키워드는 받은 것을 모두 보여 주고 검색량·경쟁으로 정렬하고 말로 거를 수 있다. 블로그 글과 뉴스는 50개를 받아 두고 10·30·50개 중에 골라 본다. 보는 방법은 사용자가 맡겨서 이렇게 정했다. 작은 탭은 위에 붙어 있다.
  - 0.11.1 (2026-11-18): 사용자 의견대로, 찾은 것을 작은 탭(키워드 / 블로그 글 / 뉴스)으로 나눠 하나씩 보이게 했다.
  - 접근 허용 주소가 두 곳 늘었다: `openapi.naver.com`, `api.searchad.naver.com`. 확장을 새로고침하면 크롬이 권한이 늘었다고 물을 수 있다.
  - 확인한 것: 실제 키로 블로그 글 찾기, 뉴스 찾기, 키워드 도구를 한 번씩 불러 봤고 잘 됐다 (확장에서 부를 때처럼 Origin 헤더를 붙여서도 됐다). 화면은 미리보기와 가짜 응답으로 확인했다. **설치한 확장에서 직접 불러 보지는 못했다.**
  - 참고 뉴스용 프롬프트는 확장에만 있는 글이다 (`research.news_head`, `research.news_item`, 없어도 되는 글). 사용자가 올리라고 해서 2026-11-18에 서버의 묶음을 새로 올렸다 (서버에서 `research.news_*`가 들어간 것을 확인했다). 확장에서는 [프롬프트 새로 받기]를 눌러야 받는다.
  - 아직 없는 것: 검색량의 달별 흐름(데이터랩), 자동완성 키워드, SEO 8단계와 사진 리뷰에 자료 넘기기, 블로그 글의 본문 읽기(남의 글을 긁지 않으려고 넣지 않았다).
- **사진으로 리뷰 쓰기** (확장 0.9.0, 2026-11-18):
  - 사용자 요청: 제품을 사서 사진을 올리면, AI가 사진을 보고 내 말투로 리뷰 글을 써 주면 좋겠다.
  - 새 탭 "사진 리뷰" (`review-section.ts`). 사진(10장까지)과 제품 이름, 메모, 구매 방식(내 돈 / 제공받음 / 말하지 않음)을 받아 AI에 보낸다. 사진은 1280픽셀로 줄인 사본을 사진마다 번호표("사진 1")와 함께 보낸다 (`lib/llm/client.ts`가 세 회사의 모양으로 바꾼다).
  - AI는 `[제목]` 제목 후보 3개와 `[본문]` 본문을 돌려준다. 본문에는 사진 자리 `[IMG: 사진N - 설명]`이 들어 있다. `lib/review/photo.ts`가 자리를 정리한다: 없는 번호와 겹친 번호는 지우고, 빠진 사진은 글 끝에 붙인다.
  - [채우기로 보내기]를 누르면 글과 함께 사진이 자리에 미리 골라진다 (`fill.setContent`의 세 번째 값). 올리는 것은 0.6.0의 사진 넣기와 같은 길이다.
  - 지키는 것: 사진에 보이는 것과 메모에 적은 것만 사실로 쓰게 한다. 모르는 것은 "확인 필요"로 남기고 화면에서 몇 곳인지 알려 준다. 제공받은 제품이면 글 첫머리에 밝히게 한다.
  - 내 말투: "내 말투" 탭에서 정리한 말투 카드가 있으면 그 말투로 쓴다 (체크로 끌 수 있다).
  - 프롬프트는 확장에만 있는 글이다 (`scripts/extension-prompts.ts`의 `review.*`). 묶음에서는 "없어도 되는 글"이라 예전 묶음도 그대로 쓸 수 있고, 그때는 사진 리뷰만 꺼진다. **서버의 묶음을 새로 올려야 사용자가 쓸 수 있다** (`npm run prompts:push`). 사용자가 올리라고 해서 2026-11-18에 올렸다 (서버에서 `review.*`와 `cards.rewrite`가 들어간 것을 확인했다). 확장에서는 설정 탭의 [프롬프트 새로 받기]를 눌러야 받는다.
  - 아직 없는 것: 다른 사람의 리뷰 글에서 배우기 (사용자가 말을 꺼냈다. 남의 문장을 가져오지 않고 글의 구성만 참고하는 방식으로 제안했다. 정하지 않았다), 만든 리뷰를 기록에 남기기, 제품 정보를 쇼핑몰 주소에서 읽어 오기.
- **AI 모델 최신화** (확장 0.12.1, 2026-11-18): 사용자가 모델을 최신으로 맞춰 달라고 했다. 세 회사의 문서에서 지금의 모델을 확인했다 (`DESIGN-detail.md` 6.4의 표). 확장은 모델 이름을 적어 두지 않아서, 처음 골라 주는 규칙만 고쳤다 (Claude는 Opus 5.5, GPT는 6.2 Sol, Gemini는 4 Hydrogen). 받은 지 일주일이 넘은 모델 목록은 패널을 열 때 자동으로 새로 받고, 고른 모델이 없어졌으면 다시 골라 알려 준다. **웹도 고쳤다** (사용자 확인을 받음): 웹에는 2025년 모델이 적혀 있었고 기본 모델 둘이 2026-11-30 ~ 12-01에 꺼진다. `web/lib/llm.ts`(기본 모델, 호출 코드), `web/app/settings/page.tsx`(목록), `web/lib/llm-pricing.ts`(요금)를 고쳤다. 자세한 것은 `DESIGN-detail.md` 6.4. 실제 모델 목록(무료)으로 이름을 확인했고, 진짜로 짧게 불러 봤다: Gemini 4 Hydrogen과 GPT-6.2 Sol은 웹의 호출 코드, 확장의 호출 코드, 사진 보내기가 모두 됐다. **Claude는 그 키의 계정에 충전한 돈이 없어서 확인하지 못했다.** `gemini-2.5-pro`는 이 키에서 이미 안 된다 (지금 배포된 웹의 Gemini 기본 모델이 이미 실패하고 있을 수 있다). 확장 0.12.2는 전에 자동으로 골라졌던 모델을 새 추천으로 한 번 옮겨 준다. **이 브랜치를 `main`에 합쳐 배포해야 실제 웹에 반영된다. 꺼지는 날 전에 해야 한다.**
- 아직 확인하지 못한 것:
  - **설치한 확장에서 진짜 AI 키로 글이 만들어지는지.** 2026-11-18에 확장의 호출 코드를 컴퓨터에서 직접 돌려 Gemini와 GPT를 짧게 불러 봤고 (글, 사진) 잘 됐다. 크롬에 설치한 확장의 화면에서 긴 글을 만들어 보는 것, 그리고 Claude는 아직 확인하지 못했다.
  - **실제 네이버 글쓰기 화면에서 사진이 들어가는지** (0.6.0). 가짜 화면으로만 시험했다. 블로그용 카드(0.7.0)도 같은 길로 올라가므로 함께 확인한다.
  - **진짜 AI에 사진을 보내 리뷰 글이 만들어지는지** (0.9.0). 세 회사에 사진을 보내는 요청의 모양은 가짜 서버로만 시험했다. 고른 모델이 사진을 읽지 못하면 오류가 난다.
  - 크롬에 설치한 확장에서 묶음 파일을 고르는 창이 잘 뜨는지 (미리보기에서는 파일 창을 시험하지 못했다).
  - **확장이 실제 블로그 탭 안에서 글을 읽어 오는지.** 글 목록과 본문을 알아보는 코드는 받아 둔 실제 공개 글로 확인했다. 탭 안에 코드를 넣어 읽는 과정은 가짜 탭으로만 시험했다.
  - 임시저장한 글을 다시 열어도 그대로인지. 사용자가 시험이 잘 됐다고 했지만, 다시 열어 본 것인지는 듣지 못했다.

## 지킬 것

1. **발행 버튼은 코드로 누르지 않는다.** 임시저장은 선택 기능을 켰을 때만 한다.
2. **기존 폴더는 필요한 만큼만 고친다.** `web`에는 설계 문서에 적힌 것만 더한다. `local_agent`와 `jobs` 표는 건드리지 않는다.
3. **다른 확장 프로그램의 코드, 프롬프트 문장, 서체는 가져오지 않는다.** 구조만 참고했다. 에디터 부품 모양은 내 에디터에서 직접 읽은 견본으로 만든다.
4. **프롬프트는 확장 파일에 넣지 않는다.**
5. **커밋은 요청받았을 때만 한다.**

## 폴더 위치

- 이 프로젝트는 `~/dev/blog_studio`에 있다. 2026-11-16에 iCloud가 동기화하는 문서 폴더에서 옮겼다.
- 예전 위치(`문서/00_project/...`)를 가리키는 메모나 설정이 남아 있으면 새 위치로 고친다.
- `~/dev`는 iCloud에 올라가지 않는다. 백업은 GitHub로 한다.
- 파이썬 가상환경(`venv`)은 폴더를 옮기면 깨진다. 로컬 에이전트를 다시 쓸 때는 가상환경을 새로 만든다.
- 코드 프로젝트를 문서 폴더나 데스크탑에 두지 않는다. iCloud가 `node_modules`와 git 내부 파일까지 올리고, 저장 공간 최적화가 파일을 이 맥에서 지울 수 있다.
